# Grocery POS V1: product codes, barcode scanning, and internal labels

**Date:** 2026-08-10  
**Status:** Specified after grill-with-docs review  
**Scope:** Planning only; no application code is included

## Outcome

Hisab Grocery POS V1 will support:

1. One optional Product Code per Product.
2. Manufacturer EAN/UPC codes stored exactly as scanned, such as `7622202334009`.
3. Organization-internal EAN-13 labels generated from the GS1 `04` restricted-circulation range for uncoded fixed-count Products.
4. USB/Bluetooth HID scanner lookup and scan-to-cart billing.
5. An Organization-level Barcode Scanning setting.
6. A Store Device-level Direct Barcode Scan preference.

V1 explicitly excludes multiple barcodes per Product, variable-weight/fractional quantities, weighing-scale barcode parsing, inventory/stock accounting, batches/expiry, and case-unit conversion.

## Approved decisions

| Decision | V1 rule |
| --- | --- |
| Product Code cardinality | Zero or one Product Code per Product |
| Manufacturer code | Store the exact scanned value as text |
| Code uniqueness | One Product Code maps to only one Product in an Organization |
| Variants | Different size, flavour, weight, bottle, pack, or case is a separate Product |
| Uncoded fixed-count goods | Generate a store-only `04` RCN-13 with a valid check digit |
| Fake `890` identifiers | Never generate them; globally usable Indian GS1 identifiers come from GS1 India |
| Scanner | Begin with USB/Bluetooth HID keyboard scanners |
| MRP | Deferred outside V1 |
| Direct scanning | Store Device preference |
| Sale quantity | Positive whole-number quantity only |
| Multiple barcodes | Deferred beyond V1 |
| Variable weight and scales | Deferred beyond V1 |

## Domain language

### Product Code

The single optional identifier Hisab uses to find a Product during scanning.

- For a packaged Product, it is normally the complete manufacturer value, for example `7622202334009`.
- For an uncoded Product, it may be a generated internal RCN-13, for example `0400000001234`.
- It is always stored as text. Leading zeroes are significant.
- It is unique only within an Organization from Hisab's database perspective.

### Manufacturer Product Code

An identifier already printed on the Product by its manufacturer or brand owner. Hisab stores and uses it; Hisab does not generate or own it.

### Internal Product Code

A store-only identifier generated by Hisab for a fixed-count Product that has no manufacturer barcode. It is not a globally registered GTIN.

### Selling Price

The trusted catalog price. The existing Product `price` remains the selling price in V1, while the existing discount is applied separately.

### Direct Barcode Scan

A Store Device behavior that captures scanner input immediately while the Product billing panel is open. It does not change Product data.

## Current repository fit

The existing design makes this a contained catalog and POS extension:

- `packages/types/src/modules/catalog/catalog.schema.ts` defines Products without Product Code fields.
- `apps/backend/db/migrations/20260625150000_create_categories_and_products.sql` creates organization-scoped Products and already provides a composite tenant anchor.
- `apps/backend/src/modules/pos/pos.routes.ts` returns the Organization catalog to an authenticated Store Device.
- `apps/web/src/pages/billing-page.tsx` loads the full catalog, filters by name/category, and already has `addProductToBill`/`addPlainProductToBill` behavior that adds or increments a cart line.
- `CONTEXT.md`, the shared billing schema, database, services, and UI already enforce whole-count Sale quantities. V1 keeps this rule unchanged.

At roughly 650 Products, loading the Product Codes with the POS catalog and building an in-memory lookup map is small and avoids a network request for every scan.

## V1 data model

### Products

Add these fields to `products`:

```text
product_code       varchar(128) null
product_code_kind  manufacturer | internal_rcn null
```

Required rules:

- Add a partial unique index on `(organization_id, product_code)` where `product_code IS NOT NULL`.
- Store `product_code` as text; never coerce it to a JavaScript or SQL number.
- Remove only scanner transport terminators; preserve the manufacturer Product Code as opaque text, including meaningful leading zeroes and any other code characters.
- Require `product_code_kind` whenever `product_code` exists.
- Set `product_code_kind = manufacturer` for scanned/entered packaging codes.
- Set `product_code_kind = internal_rcn` only through the server-owned generator.

### Why one Product column?

The approved V1 rule is one Product Code per Product. A nullable Product column is the smallest honest model and matches the Vyapar-style Item Code experience.

Do not create `product_barcodes` or `is_primary` in V1. If real operational evidence later proves that aliases are required, migrate the Product column into a one-to-many table without changing the meaning of existing values.

Replacing or clearing a Product Code in V1 immediately stops the old value from resolving and releases it for reassignment. The admin UI must warn about existing stock carrying the old label.

### Organization catalog settings

Create a one-to-one `organization_catalog_settings` table:

```text
organization_id          uuid primary key
barcode_scanning_enabled boolean not null default false
created_at                timestamptz not null
updated_at                timestamptz not null
```

Settings control UI behavior, not data deletion:

- Disabling Barcode Scanning hides Product Code management and scanning controls but retains saved codes.
- A future Grocery organization template should default Barcode Scanning to enabled.

### Store Device POS settings

Create a one-to-one `store_device_pos_settings` table:

```text
device_id                   uuid primary key
organization_id             uuid not null
store_id                    uuid not null
direct_barcode_scan_enabled boolean not null default false
created_at                  timestamptz not null
updated_at                  timestamptz not null
```

Use composite foreign keys so the Device, Store, and Organization scopes cannot disagree.

Direct capture belongs to the Store Device because one counter may have a scanner while another does not.

### Internal Product Code sequence

Create `organization_product_code_sequences`:

```text
organization_id      uuid primary key
next_item_reference  bigint not null default 1
updated_at            timestamptz not null
```

Generate an internal value transactionally:

```text
04 + zero-padded 10-digit Organization sequence + GS1 check digit
```

Example valid value:

```text
0400000001234
```

Generation requirements:

- Lock and increment the Organization counter in the Product create/update transaction.
- Calculate the check digit on the backend.
- Use the Product unique index as the final collision authority.
- Never wrap or automatically recycle exhausted sequence values. A released internal code may be explicitly reassigned by an administrator after a warning that old labels could identify a different Product.
- Show `Store-only code; not a globally registered GTIN` in the admin UI and label preview.
- Never generate an internal code automatically when the administrator scans a manufacturer code.

Do not change `sale_items.quantity`; it remains integer-based in this V1.

## API and service plan

### Catalog Product contracts

Extend Product create/update/read contracts with:

```text
productCode
productCodeKind
```

Backend responsibilities:

- Remove only scanner transport terminators and preserve the received code text.
- Organization-scoped duplicate detection with a friendly error.
- Database constraint handling for concurrent duplicate writes.
- Treat manufacturer Product Codes as opaque text; do not validate barcode shape, check digits, GS1 ownership, or product metadata.
- Server-owned internal RCN generation.

Duplicate response example:

```text
Product code 7622202334009 is already assigned to "Dairy Milk 20 g".
```

Opaque Product Code storage does not prove Product ownership or name; checkout does not depend on an external service.

### Settings contracts

Add admin-authenticated endpoints to read/update Organization catalog settings.

Add Device-authenticated or appropriately admin-managed endpoints to read/update Store Device POS settings. A Store Device may update its Direct Scan preference but not Organization-wide Barcode settings unless an admin flow explicitly permits it.

### POS catalog

Return active Product Codes, code kinds, price, and discount from the existing device-scoped Product catalog endpoint.

Build:

```text
Map<ProductCode, ProductResponseDTO>
```

The mapping is Organization-scoped by the authenticated Store Device session. Checkout remains local and fast; it does not call GS1 or an internet Product database per scan.

### Billing

Keep the existing selection-only billing payload:

```text
productId + whole-number quantity + configuration selections
```

The backend continues to load trusted Product price/discount and calculate all Sale snapshots without accepting cashier-authored prices.

## Product-management UX

Product Code creation, replacement, clearing, and released internal-code reuse are administrator-only operations. Store Devices may scan codes for billing but cannot change catalog identity.

When Barcode Scanning is enabled, the Product form shows one **Product Code** field with:

- Scan manufacturer code.
- Type/paste manufacturer code.
- Generate store-only code.
- Reuse released internal code through a separate administrator action.
- Clear/replace code with confirmation.
- Code kind indicator.
- Duplicate messages.

Replacing warning:

```text
Existing stock carrying the old Product Code will stop scanning.
Replace the code anyway?
```

Do not show multiple-code lists, aliases, or primary-code controls.

Never silently create a Product from an unknown barcode. Bulk CSV import and Scan-and-Link onboarding are deferred beyond V1.

Use the existing selling-price and discount calculation.

## POS scanning UX

### Hardware behavior

Support a USB/Bluetooth HID scanner configured with an Enter suffix.

- A visible `Scan or type Product Code` input is available whenever Barcode Scanning is enabled.
- Direct Barcode Scan automatically focuses/captures while the Product billing panel is open.
- Provide a clear pause/resume action so normal search/typing is not intercepted.
- Ignore global capture while the cashier is using another editable field or dialog unless the dedicated scan field owns focus.
- Clear and refocus the scan input after every result.
- Keep manual Product search and category browsing available.

### Successful scan

For `7622202334009`:

1. Receive the complete string terminated by Enter.
2. Remove only surrounding whitespace/control terminators.
3. Exact lookup in the Organization Product map.
4. Confirm the Product is active.
5. Reuse `addProductToBill` and the existing Product-card action rules.
6. A simple Product is added with quantity `1`; another intentional scan increments it.
7. A configurable Product opens its existing customization/configuration flow rather than silently choosing options.
8. Show Product name, updated quantity, and a success sound/visual cue.

Do not debounce separate HID scans. If camera scanning is added later, camera callbacks may use a separate same-code cooldown.

### Error behavior

Unknown, inactive, or duplicate Product Codes never change the cart.

An inactive Product keeps its Product Code reserved. Only explicit clearing, replacement, or permanent Product deletion releases the value for reassignment.

Code release occurs only after Product deletion succeeds. If deletion is blocked by existing sales history or bundle/Combo dependencies, the Product and its code reservation remain unchanged.

Examples:

```text
Unknown Product Code: 1234567890123
Product is inactive: Old Dairy Milk Pack
Product Code is already assigned to Dairy Milk 20 g
```

An unknown scan should retain/show the scanned value and offer:

- Search Products manually.
- Copy the value.
- Send it to the admin linking workflow.

A Device session must not gain catalog-admin permission merely because a barcode is unknown.

## Deferred pricing work

MRP storage, validation, snapshots, and receipt presentation are outside V1 and require a separate future specification.

## Internal label printing

For an `internal_rcn` Product Code:

- Render EAN-13 using the exact 13 digits.
- Print human-readable digits below the bars.
- Preserve required quiet zones.
- Default to black bars on white.
- Allow Product name and selling price outside the quiet zones.
- Support A4 label sheets and a dedicated thermal-label layout.
- Allow number of copies and A4 starting position.
- Keep label printing separate from the existing ESC/POS receipt module.
- Require a test print and scan before bulk printing.

If visible selling price is printed on the sticker, warn that price changes require reprinting the sticker even though the encoded Product Code stays the same.

## Migration and compatibility

1. Add Product Code fields as nullable/default-safe changes. Existing Products receive no Product Code.
2. Add settings rows for existing Organizations and Store Devices with features disabled by default.
3. Explicitly enable Barcode Scanning and Direct Scan for the grocery client's intended counter(s).
4. Do not alter Product IDs, Sale quantities, existing prices, Sale totals, receipt history, or configured-item behavior.

## V1 implementation slices

### Slice 1: Settings and Product foundation

- Product Code/kind database migration.
- Settings tables and backfill.
- Shared DTOs and validation.
- Repository/service/routes.
- Admin settings and Product-form UI.

### Slice 2: Scan-to-cart

- POS Product Code map.
- Dedicated scan input.
- Store Device Direct Scan preference.
- Reuse existing cart/configuration actions.
- Success/error feedback and unknown-code recovery.

### Slice 3: Internal code generation and label printing

- Transaction-safe Organization sequence.
- `04` RCN-13 and check-digit generator.
- Label preview/copies/A4/thermal layouts.
- Test using the client's real scanner, label paper, printer, and POS Device.

### Slice 4: Rollout and monitoring

- Enable Direct Scan per production Store Device.
- Track unknown scans, duplicate attempts, invalid codes, and scan-to-cart failures.
- Train cashiers on pause/resume, manual search, and unknown-code recovery.

All four slices are part of Grocery POS V1. Feature settings remain off until the Store's individual Product setup and hardware tests are complete.

## Test plan and acceptance criteria

### Product Code

- `7622202334009` round-trips unchanged through database, API, form, and scanner lookup.
- Leading-zero Product Codes round-trip unchanged.
- A Product can have at most one Product Code.
- Two Products in one Organization cannot share a Product Code, including concurrent writes.
- The same store-only Product Code may exist in separate Organizations without cross-tenant resolution.
- Replacing a Product Code requires explicit confirmation.
- Unknown/inactive Product Codes never mutate the cart.

### Internal generation

- Generated value is exactly 13 digits, begins with `04`, and has the correct check digit.
- Concurrent generation cannot duplicate a value within an Organization.
- Exhausted sequence space fails clearly rather than wrapping.
- A released internal code can be reassigned only through an explicit administrator action and warning; automatic generation continues forward.
- Generated labels scan on the client's production hardware.

### Settings and scanner

- Disabling a feature hides behavior without deleting saved Product data.
- Direct Scan preference is isolated per Store Device.
- Scanner input does not steal normal typing while paused or inside unrelated forms.
- Repeated intentional HID scans increment quantity without being suppressed.
- Configurable Products continue to open the correct existing flow.

### Regression

- Existing whole-count quantity validation remains unchanged.
- Existing bundles, Combos, Add-Ons, discounts, drafts, commits, payments, receipts, and reporting continue to pass.
- Products without Product Codes remain searchable and billable manually.

## Explicitly outside V1

- Multiple Product Codes, aliases, or primary-code selection.
- Fractional Sale quantities such as `1.275 kg`.
- Variable-weight Products or weighing-scale barcode parsing.
- Price-embedded or weight-embedded dynamic barcodes.
- Automatic internet lookup of Product name/price.
- Globally registered barcode issuance.
- Bulk CSV Product Code import and Scan-and-Link onboarding.
- MRP storage, validation, snapshots, and receipt presentation.
- Inventory stock deduction, valuation, low-stock alerts, or transfers.
- Batch, expiry, and manufacturing-date tracking.
- Case/piece or other unit conversions.

These exclusions are intentional. They should be separate future specifications rather than hidden extension points in this implementation.

## Final implementation rule

Grocery POS V1 stays deliberately simple: one optional static Product Code finds one Product inside an Organization; the backend supplies trusted selling price and discount; all Sale quantities remain whole counts. MRP is deferred. Hisab generates `04` store-only labels only for uncoded Products, and Direct Scan is enabled per Store Device after catalog and hardware verification.
