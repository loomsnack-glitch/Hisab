# Grocery POS V1: Product Codes, Scan-to-Cart, and Internal Labels

## Problem Statement

The grocery store needs a reliable way to identify Products at the counter without making cashiers search a catalog for every item. Packaged Products already have manufacturer codes, while some fixed-count Products need store-only labels. The store also needs a safe way for administrators to manage these codes and print labels without changing Hisab's existing trusted pricing, whole-count billing, Product lifecycle, or configured-Product behavior.

MRP is deliberately excluded from this V1. Bulk Product Code onboarding is also excluded; administrators will set up individual Products through the existing catalog workflow.

## Solution

Add one optional Product Code to each Product. A Manufacturer Product Code is stored as opaque text exactly as received, after removing only the scanner's transport terminator. An Internal Product Code is generated by Hisab for eligible uncoded fixed-count Products as a store-only 13-digit `04` code with a calculated check digit.

Expose Product Codes through the existing organization catalog and device-scoped POS catalog. The POS builds an Organization-scoped lookup map and uses it to add Products to the existing bill. Repeated intentional scans increment whole-number quantity; configurable Products continue through their existing configuration flow.

Add an Organization-level Barcode Scanning setting and a Store Device-level Direct Barcode Scan preference. Catalog identity changes remain administrator-only. Released codes stop resolving immediately and become available for reassignment, but released Internal Product Codes may be reused only through an explicit administrator action. Automatic Internal Product Code generation continues forward and does not recycle released or exhausted sequence values.

Add separate internal-label generation and printing for A4 sheets and thermal labels. Labels preserve barcode quiet zones, show the exact encoded digits, support optional Product name and selling price text, and require a successful test print and scan before bulk printing.

## User Stories

1. As an organization administrator, I want to assign zero or one Product Code to a Product, so that every scan resolves deterministically.
2. As an organization administrator, I want to enter a Manufacturer Product Code manually, so that I can configure Products when a scanner is unavailable.
3. As an organization administrator, I want to scan a manufacturer's code into the Product form, so that I can save the received code without retyping it.
4. As an organization administrator, I want Manufacturer Product Codes stored as opaque text, so that leading zeroes and nonnumeric manufacturer values are preserved.
5. As an organization administrator, I want no barcode-shape, check-digit, GS1-ownership, or product-metadata validation on Manufacturer Product Codes, so that Hisab accepts the value as it arrives.
6. As an administrator, I want only scanner transport terminators removed, so that the stored code is otherwise identical to the received code.
7. As an organization administrator, I want duplicate Product Codes rejected within my Organization, so that a scan cannot resolve to two Products.
8. As an organization administrator, I want the same Product Code to be usable in a different Organization, so that tenant boundaries remain independent.
9. As an organization administrator, I want to see whether a Product Code is manufacturer-supplied or internally generated, so that I understand its ownership and reuse rules.
10. As an organization administrator, I want to generate a store-only code for an eligible uncoded fixed-count Product, so that the Product can receive a scannable internal label.
11. As an organization administrator, I want the internal generator to create a 13-digit code beginning with `04` and containing a calculated check digit, so that printed labels are scanner-compatible.
12. As an organization administrator, I want internal-code generation to be transactional and Organization-scoped, so that concurrent administrators cannot receive the same generated code.
13. As an organization administrator, I want automatic generation to advance rather than recycle released values, so that old labels are not silently reassigned.
14. As an organization administrator, I want a dedicated reuse action for a released Internal Product Code, so that reusing an old label is deliberate.
15. As an organization administrator, I want a warning before reusing a released Internal Product Code, so that I understand old labels may now identify a different Product.
16. As an organization administrator, I want to clear or replace a Product Code with confirmation, so that accidental catalog identity changes are avoided.
17. As an organization administrator, I want a replacement warning explaining that old labels stop scanning, so that I can account for labels already in circulation.
18. As an organization administrator, I want Product Code operations restricted to administrator permissions, so that cashiers cannot change catalog identity.
19. As an organization administrator, I want inactive Products to retain their Product Code reservation, so that an old label cannot be reassigned while the Product is merely unavailable.
20. As an organization administrator, I want a successfully deleted Product's code released, so that the value can be reused later.
21. As an organization administrator, I want a failed or blocked deletion to leave the code reservation unchanged, so that a code is never released without the Product actually being deleted.
22. As an organization administrator, I want Product Code changes to preserve existing Product IDs and Product pricing, so that catalog identity changes do not rewrite billing history.
23. As an organization administrator, I want Barcode Scanning to be enabled or disabled at the Organization level, so that the store can control whether code-management and scan controls are available.
24. As an organization administrator, I want disabling Barcode Scanning to retain saved Product Codes, so that temporarily hiding the feature does not destroy catalog data.
25. As an organization administrator, I want the existing organization and device defaults to remain safe and disabled until explicitly enabled, so that rollout is controlled.
26. As a Store Device operator, I want the POS catalog to include active Product Codes, so that scans can resolve without a network request per item.
27. As a Store Device operator, I want Direct Barcode Scan enabled independently per Store Device, so that only counters with compatible hardware intercept scanner input.
28. As a Store Device operator, I want a visible scan field while Barcode Scanning is enabled, so that I can scan or type a Product Code deliberately.
29. As a Store Device operator, I want Direct Barcode Scan to have pause and resume controls, so that ordinary catalog search and typing remain usable.
30. As a Store Device operator, I want scanner capture ignored while I am editing another field or dialog, so that scanner input does not corrupt unrelated data.
31. As a Store Device operator, I want the scan field cleared and refocused after each result, so that the next scan is ready immediately.
32. As a Store Device operator, I want a known simple Product scan to add one unit to the current bill, so that checkout is fast.
33. As a Store Device operator, I want repeated intentional scans of the same Product to increment whole-number quantity, so that I can scan multiple units efficiently.
34. As a Store Device operator, I want a configurable Product scan to open its existing configuration flow, so that options are never silently guessed.
35. As a Store Device operator, I want manual Product search and category browsing to remain available, so that Products without codes and failed scans remain billable.
36. As a Store Device operator, I want an unknown scan to leave the bill unchanged, so that an unconfigured barcode cannot create an accidental line.
37. As a Store Device operator, I want an unknown scan's received value shown and copyable, so that I can report or configure it without retyping.
38. As a Store Device operator, I want to search manually after an unknown scan, so that I can complete the bill without catalog-admin access.
39. As a Store Device operator, I want to send an unknown value to an administrator linking workflow, so that missing codes can be resolved later.
40. As a Store Device operator, I want an inactive Product scan to leave the bill unchanged and explain that the Product is inactive, so that unavailable catalog items cannot enter new bills.
41. As a Store Device operator, I want duplicate-assignment errors to be clear to administrators, so that the conflicting Product can be found and resolved.
42. As a Store Device operator, I want a success cue showing the Product name and updated quantity, so that I can confirm each scan without inspecting the whole bill.
43. As an organization administrator, I want to print an internal Product Code as an EAN-13 label, so that uncoded fixed-count Products can be scanned at checkout.
44. As an organization administrator, I want human-readable digits printed below the bars, so that staff can identify or recover a code visually.
45. As an organization administrator, I want required barcode quiet zones preserved, so that scanners can reliably read the label.
46. As an organization administrator, I want black bars on a white background by default, so that labels have a dependable contrast baseline.
47. As an organization administrator, I want Product name and selling price optionally printed outside the quiet zones, so that labels are useful to staff without changing scan identity.
48. As an organization administrator, I want price-on-label warnings, so that I know a selling-price change requires label reprinting.

## Implementation Decisions

- The primary seam is the existing organization catalog Product contract/service/repository boundary, extended with an optional Product Code and its kind. The existing Product lifecycle remains authoritative for active/inactive status and deletion safety.
- The POS seam is the existing device-scoped Product catalog response. It will include active Product Codes and code kinds, allowing the POS client to construct one Organization-scoped lookup map alongside the current catalog.
- The billing seam is the existing Product-selection and add-to-bill behavior. Scanning supplies Product identity only; it does not supply price, discount, quantity beyond the scanner event, or configuration selections.
- Internal label printing is a separate presentation seam from the existing ESC/POS receipt module. It owns barcode rendering, quiet zones, A4 placement, thermal layout, preview, copy count, and test-print workflow.
- A Product has at most one active Product Code. Multiple codes, aliases, primary-code selection, and a Product Code history table are outside V1.
- `product_code` is nullable text. `product_code_kind` is required when a code exists and is either `manufacturer` or `internal_rcn`.
- Manufacturer Product Codes are opaque text. The system removes only scanner transport terminators and preserves all other received characters. It performs no structural barcode, check-digit, GS1 ownership, or product-metadata validation.
- A nullable Product Code is unique within an Organization. The database uniqueness rule is the final authority for concurrent writes, and the service returns a friendly duplicate-assignment error.
- Codes are not globally unique in Hisab. The same value may exist in different Organizations and cannot resolve across tenant boundaries.
- Product Code creation, replacement, clearing, and released internal-code reuse are administrator-only operations. Store Devices can consume the catalog for billing but cannot mutate Product identity.
- Clearing, replacing, or successfully deleting a Product Code releases the old value immediately. Inactive Products retain their code reservation. A blocked Product deletion releases nothing.
- Existing Product deletion rules remain authoritative: deletion remains blocked where the current catalog prevents deletion because of sales history or bundle/Combo dependencies.
- Internal Product Codes are available only for eligible uncoded fixed-count Products. Hisab generates a 13-digit `04` code with a calculated check digit using a transactional Organization sequence.
- The automatic internal sequence advances and does not recycle released or exhausted values. A released internal value can be assigned only through a dedicated administrator reuse action with an explicit warning.
- Internal-code generation is never triggered implicitly by entering or scanning a Manufacturer Product Code.
- Existing Organizations and Store Devices receive disabled-safe defaults. Barcode Scanning is Organization-level; Direct Barcode Scan is Store Device-level.
- Disabling Barcode Scanning hides management and scanning controls but retains saved Product Codes. It does not grant cashier or device permission to change catalog identity.
- The device-scoped POS catalog returns active Products with their Product Codes, code kinds, selling prices, and discounts. The lookup map is scoped by the authenticated Store Device's Organization.
- Scanner input uses USB/Bluetooth HID keyboard scanners configured with an Enter suffix. The Enter suffix is framing, not Product Code data.
- Direct capture is paused while unrelated editable fields or dialogs own focus. Manual search and category browsing remain available.
- Successful simple scans reuse existing add-to-bill behavior with quantity one. Repeated intentional scans increment the existing whole-number quantity. Configurable Products enter their existing configuration flow.
- Unknown, inactive, or duplicate-resolution failures never mutate the bill. Unknown values remain visible and support manual search, copying, and administrator linking recovery.
- No Product is silently created from an unknown scan. An unknown scan cannot elevate a Store Device into catalog administration.
- Label output uses exact internal-code digits, human-readable digits, preserved quiet zones, black-on-white defaults, optional Product name and selling price text, A4 and thermal layouts, copy count, and A4 starting position.
- A test print and successful scan on production-like hardware and label stock are required before bulk label printing.
- MRP storage, MRP validation, MRP snapshots, MRP display, and MRP receipt presentation are not part of this specification.
- Bulk CSV import, Scan-and-Link onboarding, inventory accounting, batches, expiry, variable-weight barcodes, scale parsing, dynamic price/weight barcodes, and case-unit conversion are not part of this specification.

## Testing Decisions

- Tests should assert externally visible behavior at the highest existing seam: shared catalog schemas/contracts, catalog service behavior, database constraints/transactions, device-scoped catalog responses, POS scan behavior, billing integration behavior, and rendered label output.
- Tests should not assert private helper structure, internal map implementation, component arrangement, or a particular SQL query shape beyond observable constraints and transaction outcomes.
- Shared catalog contract tests should cover optional code fields, required code kind, opaque string round-trips, leading zeroes, empty/cleared codes, and rejection of duplicate assignments at the contract boundary where applicable.
- Catalog service tests should cover administrator-only Product Code operations, duplicate lookup errors, exact-value preservation, manufacturer versus internal code kind, clear/replace warnings, internal-code generation, explicit released-code reuse, and failed deletion preserving code assignment.
- Repository/database tests should cover nullable Organization-scoped uniqueness, concurrent duplicate writes, Organization isolation, transactional sequence allocation, correct generated check digits, non-recycling automatic generation, and release only after successful deletion.
- POS catalog tests should cover active Product Code projection, Organization-scoped lookup data, inactive Product handling, and retention of existing selling price/discount behavior.
- Billing/UI tests should cover one successful scan, repeated scans incrementing whole-number quantity, configurable Products opening the existing flow, unknown/inactive scans leaving the bill unchanged, pause/resume behavior, focus ownership, manual search fallback, and success/error feedback.
- Label-printing tests should cover exact 13-digit rendering, check digit, quiet zones, human-readable digits, optional Product text, selling-price warning, A4 starting position, copy count, thermal layout, and test-print gating.
- Regression tests should reuse the existing catalog, POS, and billing test patterns for Product lifecycle, device-authenticated catalog loading, whole-count quantities, drafts, configured Products, discounts, payments, receipts, and reporting.
- Hardware acceptance should use the store's actual or production-equivalent HID scanner, label printer, label stock, and POS Device. A generated label is accepted only after it scans back to the intended Product.

## Out of Scope

- MRP in every form: storage, settings, validation, snapshots, cart display, bill display, receipt output, and reporting.
- Bulk CSV Product Code import, dry-run onboarding, and Scan-and-Link workflows.
- Multiple Product Codes, aliases, alternate codes, code history, or primary-code selection.
- Fractional or variable-weight quantities, weighing-scale barcode parsing, price-embedded barcodes, and weight-embedded barcodes.
- Automatic internet lookup of Product names, prices, ownership, or GS1 data.
- Issuing globally registered identifiers or presenting internal codes as globally registered GTINs.
- Inventory stock deduction, valuation, transfers, low-stock alerts, batch tracking, expiry tracking, manufacturing dates, and case/piece conversion.
- Cashier-authored Product Codes, prices, discounts, or catalog mutations from a Store Device.
- A Product Code becoming an alias after replacement; the old value stops resolving immediately.

## Further Notes

- The existing Product `price` and discount remain the trusted catalog inputs for billing. Barcode scanning only finds the Product.
- The existing whole-count Sale Quantity remains unchanged.
- The existing Product ID, sale snapshots, historical receipts, and configured-Product behavior remain unchanged by scanning.
- A code released by replacement or deletion may later identify a different Product. The administrator warning and explicit internal-code reuse action are therefore part of the safety boundary.
- Existing Product deletion may be blocked by the current catalog rules. The barcode feature must not weaken those rules or release a code before deletion succeeds.
- Feature rollout should enable Barcode Scanning and Direct Barcode Scan only after individual Product setup and hardware tests are complete.
- This specification supersedes the MRP portions of the earlier planning note for V1. The earlier research note remains background research, not V1 scope.
